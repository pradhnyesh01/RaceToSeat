# naive is the sole adversarial-deadlock demo; other deadlock-capable mechanisms ship pre-ordered

`naive`, `unique_constraint`, `optimistic`, and `serializable` all perform a blocking `UPDATE` on `seats` as part of their per-seat write, so all four can deadlock across an unordered multi-seat set; `pessimistic` (`FOR UPDATE NOWAIT`) and `advisory` (`pg_try_advisory_xact_lock`) cannot (ADR-0006). Rather than taking each of the four deadlock-capable mechanisms through its own genuinely-broken-then-fixed before/after cycle, only `naive` gets that treatment (Phase 3, todo.md), mirroring Phase 0's naive/Exhibit A precedent: its multi-seat extension is committed without consistent seat-id ordering first, run against a real adversarial overlapping-seat-set workload to capture a genuine nonzero deadlock rate, then fixed with ordering and re-measured for the "after." `unique_constraint`, `optimistic`, and `serializable` ship with ordering applied from their first multi-seat commit, with no separate demo — the underlying Postgres phenomenon (an unordered wait-for cycle on row locks) is identical across all four, so re-proving it mechanism-by-mechanism would spend real implementation time on evidence already established once, against todo.md's own priority note to keep Phase 3 inside its allotted share of the project timeline.

## Update (issue #26, Exhibit D)

Two corrections from measuring `naive`'s actual "before" state, not assumed:

1. **The blocking `UPDATE` was never the deadlock source.** `EXPLAIN` and repeated adversarial-load runs (`deadlock-pairs.k6.js`, issue #25) confirm Postgres plans `UPDATE seats ... WHERE id = ANY($ids)` as an index/bitmap-heap scan whose row-visitation order is plan-determined (physical/index layout), not array-order-determined — two opposite-order requests for the same seat pair lock those rows in the *same* order there, so this statement can't deadlock regardless of ordering. The real cycle is in the batched `INSERT INTO booking_seats ... SELECT unnest($ids)` that precedes it: `unnest()` preserves array order, so two concurrent opposite-order requests really do insert-then-block on each other's uncommitted `booking_seats_seat_id_key` entry (confirmed via genuine `40P01` server errors under load). The fix (sorting `seat_ids`) and this ADR's bottom-line conclusion (one shared Postgres phenomenon, no need to re-prove per mechanism) both still hold — `unique_constraint`, `optimistic`, and `serializable` all share the identical `INSERT ... unnest($ids)` shape — but "blocking `UPDATE`" above should read "the ordered multi-row `INSERT`." See [Exhibit D](../evidence/exhibit-d-naive-multiseat-deadlock.md) for the measured evidence.
2. **"Ship with ordering applied from their first multi-seat commit" didn't happen that way.** All four mechanisms' multi-seat extensions landed together, unordered, in one Foundation commit (issue #24); `unique_constraint`, `optimistic`, and `serializable` each get their own dedicated follow-up ticket (issues #27–#29) to add ordering (plus `withDeadlockRetry` for the first two; `serializable` extends its own existing retry loop instead, per ADR-0014). This ADR's "no separate before/after demo" waiver still applies to those three tickets; it does not mean the work is already done.

## Update (issue #27)

`unique_constraint` now ships the fix: `seat_ids` sorted once, case-insensitively, before its per-seat `INSERT ... ON CONFLICT (seat_id) DO NOTHING`/`UPDATE seats` work, with the transactional attempt wrapped in `withDeadlockRetry`. Presumed same underlying phenomenon as `naive`'s (Exhibit D's `INSERT ... unnest($ids)` wait-for cycle) — `ON CONFLICT DO NOTHING` still probes the unique index per row in array order via Postgres's speculative-insertion protocol, so an unordered pair of concurrent opposite-order requests can plausibly still insert-then-block on each other's not-yet-confirmed index entry — but this ticket did not independently confirm it: a re-run of the adversarial harness (`--pattern deadlock-pairs --concurrency 1500 --repeat 3`, twice) against the fixed code measured zero deadlocks, zero retry-exhaustion, and zero double-booking across all runs, with `X-Booking-Retries` staying `0` throughout — meaning `withDeadlockRetry`'s fallback path was never exercised in this sample. That's consistent with the fix working (mirroring naive's "after" result, where ordering alone was already enough), but it cannot distinguish "ordering closed a real gap" from "`ON CONFLICT` was never vulnerable to this specific cycle" the way Exhibit D's genuine `40P01` server errors did for `naive`'s "before" state. No separate before/after demo, per this ADR's original waiver — this note exists so a reader doesn't overread "zero deadlocks measured" as "the deadlock was proven and reproduced here." `optimistic` and `serializable` (issues #28–#29) remain outstanding.

## Update (issue #28)

`optimistic` now ships the fix: `seat_ids` sorted once, case-insensitively, before its per-seat CAS work, with the entire transactional attempt — including the existing CAS-retry loop (ADR-0009) — wrapped in `withDeadlockRetry`. Unlike `naive`/`unique_constraint`, where the actual deadlock source turned out to be the batched `INSERT ... unnest($ids)` rather than the `UPDATE` (see the issue #26 update above), `optimistic` has no batched INSERT preceding its write: its CAS loop issues one `UPDATE ... WHERE id = $2 AND version = $3 AND status = 'available'` per seat, sequentially, in `seat_ids` order — so this mechanism is the direct match for this ADR's original "blocking `UPDATE`" framing, a genuine per-seat row-lock wait-for cycle, not a corrected-after-the-fact one. A deadlock-triggered retry re-invokes the whole callback from a fresh `BEGIN`, so the CAS loop's own `attempt` counter restarts at 0 on every such retry rather than resuming mid-loop — ADR-0009's existing CAS-conflict retry logic (when to give up, when to re-read and retry) is otherwise untouched, confirmed by `test/strategies/optimistic.test.ts` and `test/strategies/optimisticRetryExhaustion.test.ts` passing unmodified. The reported `retries` value is `deadlockAttempt + attempt` (the outer `withDeadlockRetry` attempt plus the CAS loop's own), not the CAS count alone: a deadlock-recovered success that then wins its first CAS attempt reports `1`, not `0`, so `X-Booking-Retries` still reflects total retry cost — matching `naive`'s/`unique_constraint`'s convention of always surfacing the deadlock-attempt count, rather than letting it go invisible for this one mechanism.

Re-ran the adversarial harness (`--pattern deadlock-pairs --concurrency 1500 --repeat 3`, twice) against the fixed code: the first run and the first two repeats of the second run measured zero deadlocks, zero retry-exhaustion, zero double-booking, `X-Booking-Retries` staying `0` throughout. The second run's third repeat came back with 1,904/3,000 requests failing outright (`seatsWithWinner: 1362` — many seats got no winner at all, not a double-booking) and near-zero p50 latency, alongside zero `naive`/`unique_constraint`-style deadlock signal (retries stayed `0`, no `40P01` in the server log, which stayed silent for the entire session). `netstat` confirmed 1,096 client-side connections to port 3000 sitting in `TIME_WAIT` at that moment — the residue of several consecutive 3,000-VU harness bursts run back-to-back for issues #27 and #28 in the same session — consistent with local ephemeral-port exhaustion, not an application-level fault. Waiting for `TIME_WAIT` to clear and re-running produced a third clean 3-repeat run. Same evidentiary caveat as issue #27's update: `withDeadlockRetry`'s fallback never fired in any clean run, so this can't distinguish "ordering closed a real gap" from "nothing to close," but — unlike `unique_constraint` — `optimistic`'s per-seat `UPDATE` loop is architecturally the closest match to the mechanism Exhibit D proved, so the presumption of shared cause is stronger here. No separate before/after demo, per this ADR's original waiver. `serializable` (issue #29) remains outstanding.

## Update (issue #29)

`serializable` now ships the fix, shaped differently from the other three: `seat_ids` sorted once, case-insensitively, before any write. Its write shape is the same batched `INSERT ... unnest($ids)` then single `UPDATE ... WHERE id = ANY($2)` as `naive`'s and `unique_constraint`'s (not `optimistic`'s per-seat loop) — so per this ADR's own issue #26 correction above, the deadlock risk here is specifically the ordered INSERT, not the UPDATE (whose row-visitation order is plan-determined, not array-order-determined, and so can't deadlock regardless of ordering). No `withDeadlockRetry` wrapper — that helper is explicitly not used here (see `withDeadlockRetry`'s own doc comment in `src/db/pool.ts`), since `serializable` already retries from a fresh `BEGIN` via `withSerializableTransaction` (ADR-0011), and nesting a second retry-from-`BEGIN` loop around one that already does that would double-`BEGIN` on every retry. Instead, `withSerializableTransaction`'s catch clause is extended to treat `isDeadlockDetected(err)` (`40P01`) as retriable alongside `isSerializationFailure(err)` (`40001`) — same attempt counter, same cap (`config.serializableMaxRetries`, not `deadlockMaxRetries`), same jittered backoff — so `SerializationRetriesExhaustedError` can now be thrown by either cause with no way to tell which from outside (matching this ADR's issue #26 note that ADR-0015 deliberately doesn't grow the result-kind vocabulary to disambiguate deadlock-origin retry_exhausted from any other cause). Four new unit tests in `test/db/withSerializableTransaction.test.ts` prove this directly with synthetic `{code: '40P01'}` injection (retry-and-succeed, exhaustion, and a mixed-cause sequence), mirroring the existing `40001` coverage.

**Evidentiary shape is different here than for #26-#28.** `serializable`'s baseline retry/503 rate under adversarial load is legitimately nonzero even without any deadlock involved — a documented, already-tested property (`test/strategies/serializable.test.ts`'s `checkZeroRetries: false`/`acceptableLoserStatuses: [409, 503]` concurrency test, `serializableRetryExhaustion.test.ts`), since a genuine SERIALIZABLE conflict (`40001`) is expected to fire under real contention regardless of seat-id ordering. So "zero retries measured" isn't the right bar here, and wasn't observed: three separate harness invocations (`--pattern deadlock-pairs --concurrency 1500 --repeat 3` each, 9 repeats / 27,000 requests total) measured retry counts per repeat ranging from 134 to 1,549 and occasional genuine `retry_exhausted`/503s (up to 38 in one repeat) — all consistent with ordinary `40001` contention, `booking_seats`' UNIQUE-constraint backstop (ADR-0013), or some absorbed `40P01`s indistinguishable from the former by design. The actual bar — **zero double-booking, zero unhandled errors, zero hangs** — held across all 9 repeats. 3 of the 9 repeats also showed a burst of connection-level failures (up to 385 `other` in one repeat) with silent server logs and no elevated-beyond-noise retry signal; `netstat` confirmed heavy `TIME_WAIT` buildup on port 3000 at each occurrence, matching the identical, already-diagnosed pattern from issue #28's update — local test-infrastructure noise from repeated 3,000-VU bursts on one dev machine within one session, not an application fault. No separate before/after demo, per this ADR's original waiver. Phase 3's remaining item is `pessimistic`/`advisory`'s consistency pass (issue #30).
