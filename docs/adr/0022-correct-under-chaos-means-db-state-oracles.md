# "Correct under chaos" means four DB-state Oracles; everything else is a Robustness finding

A chaos run injects a Fault between the app and Postgres and asks whether the project's guarantees survive it. Two decisions define what "survive" means, and a third governs the order of work.

**Ground truth is stored state, never HTTP responses.** A Fault makes responses unreliable in both directions: a `500` can sit on top of a transaction that committed (the connection died after `COMMIT` was sent — an *Ambiguous outcome*), and a `201` can describe state a later kill never let persist. So the verdict is read from the `seats`/`bookings`/`booking_seats`/`holds`/`hold_seats` rows after the run, by four Oracles (`load-harness/chaos/oracles.ts`): (1) **mutual exclusion** — no Seat claimed by more than one Booking/Hold, and `seats` agrees with the claim rows; (2) **no torn state** — every Booking holds exactly the Seats its Idempotency Key requested, and no Seat is `booked` without a Booking; (3) **idempotent recovery** — after the Fault clears and every Idempotency Key is re-sent, no key has more than one Booking and a key's existing Booking is unchanged by the replay (a key that lost its seat legitimately has none, so "exactly one" is not demanded of every key); (4) **liveness** — no Seat is stuck: not `held` without a Hold, not `held` past expiry, not still row-locked by a transaction that never ended. Oracle 2 needs the intended seat set per request, which the database can't supply, so the harness keeps a client-side ledger of intent (key → requested seats), re-derived from how each existing k6 script names its requests — a record the Fault can't damage. The only HTTP-derived signal that feeds any decision is the replay itself, and it is an *action*, not evidence.

**Correctness violation vs Robustness finding.** An Oracle failure is a *Correctness violation* and is the only outcome that fails Phase 6 — consistent with the project's single hard gate, zero double-booking (CLAUDE.md). A crashed process, a hung request, a masked error, a lock not released promptly — anything observed under a Fault that leaves all four Oracles intact — is a *Robustness finding*: reported, classified, ticketed for follow-up (C5), and does not fail the run. Conflating the two would let a flaky-but-safe system look unsafe, or a loud but harmless crash bury a silent one.

**Measure first, on unmodified code.** The first backend-kill run against `pessimistic` ran with `src/` untouched, and its result is recorded as found. The project's own pre-run hypotheses about production robustness (no `pool.on("error")`, no timeouts, a masked `ROLLBACK`) were treated as hypotheses to confirm, not fixed in advance — fixing first would have destroyed the only evidence of whether they were real, and which of them mattered.

One consequence needs naming. The first finding (the process crashes on the first killed connection) ends a run after one kill, hiding everything behind it, and the Oracles then judge almost nothing. The harness therefore has an opt-in `--survive-uncaught` mode that preloads an `uncaughtException` handler into the app process. It is harness scaffolding, not a mitigation: it changes nothing in `src/`, every swallowed exception is counted in the report, and runs using it are labelled as such. The unmodified result stays the recorded truth about production behavior; the scaffolded runs exist so that *later, independent* findings and the Oracles' behavior across many kills stay observable until the crash itself has its own fix ticket. Evidence from the two kinds of run is never merged.

**Amended by ADR-0032 (issue #51):** the Postgres-restart ticket adds a fifth Oracle, durability of acknowledged work, which reads one HTTP answer (a `201`'s Booking id) as a promise and checks it against stored state. It only ever convicts; the rule above, that a response is never taken as proof the system is fine, stands.
