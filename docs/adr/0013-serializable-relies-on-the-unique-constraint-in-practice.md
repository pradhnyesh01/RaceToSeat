# For the serializable mechanism, the booking_seats UNIQUE constraint resolves most real contention, not SERIALIZABLE's own conflict detection

ADR-0008 frames the shared `UNIQUE(seat_id)` constraint as defense-in-depth for every mechanism, implying SERIALIZABLE's own SSI (Serializable Snapshot Isolation) conflict detection is what primarily prevents double-booking for `BOOKING_STRATEGY=serializable`, with the constraint as a backstop that shouldn't normally fire. Empirically (confirmed with a standalone script and reproduced in `test/strategies/serializableRetryExhaustion.test.ts`'s own comments), that's backwards for this workload's actual shape: two transactions racing to book the *same* seat both attempt `INSERT INTO booking_seats`, and the unique index enforces that immediately via a plain `23505` — a physical check unaffected by isolation level — almost always *before* Postgres's SSI conflict detection has a chance to abort either transaction with `40001`. A genuine `40001` only occurs when the losing transaction's own read of the seat happens *before* the winning transaction's commit, which isn't guaranteed by ordinary concurrent timing and had to be staged deterministically (via query interception, forcing both sides to use `BEGIN ISOLATION LEVEL SERIALIZABLE`) to reproduce reliably in a test at all.

Practically: `serializable.ts` catches `booking_seats_seat_id_key`'s unique violation the same way `naive.ts` does, returning an ordinary `conflict` — this is not optional defense-in-depth for this mechanism, it's the primary way most single-seat races actually resolve. SERIALIZABLE's own guarantee still matters (and is what ADR-0011's retry loop exists for), but it's the load-bearing mechanism mainly for anomalies broader than a single-row unique-key race — e.g. write skew across multiple rows, a shape this project's single-seat booking flow doesn't currently exercise.

**Consequence**: when reading the Phase 2 comparison benchmark (PRD's conflict/retry-rate metrics, ADR-0012's retry-exhaustion column), `serializable`'s retry-exhaustion rate should not be read as "how often SERIALIZABLE conflict detection fires" — most of its ordinary `409`s never touch SSI at all. A low retry-exhaustion rate for `serializable` next to `unique_constraint`'s is expected and not evidence that SERIALIZABLE's isolation guarantee is doing less work than it claims; it means the same physical backstop both mechanisms share is doing most of the work in the common case, and SERIALIZABLE's actual value in this benchmark shows up in the same places `unique_constraint` couldn't cover on its own (see ADR-0008), even though this project's current single-seat schema doesn't exercise them.
