# Durability is a fifth Oracle, fed by what the server promised

Chaos ticket C4 (#51) restarts the Postgres *server* under load. It exists to test the one assumption the formal model makes about the database and no earlier chaos run could reach: a `COMMIT` the client has been told about is still there once the server is back (`CommittedPersists`, `formal/CrashRecovery.tla`). Four decisions follow from that, each a departure from how the other chaos tickets work.

**A fifth Oracle, not a rule inside the four.** A lost commit leaves a state the other Oracles accept: the Booking is gone, its seat is `available` again (Oracle 1, 2 and 4 see a consistent, empty seat), and the Idempotency-Key replay then books it again as an ordinary first booking (Oracle 3 sees one Booking for the key). Nothing about the end state says anything was lost. The only evidence is that a client was told it had a Booking and the database has none. So durability is its own Oracle (`load-harness/chaos/durabilityOracle.ts`), reported as Oracle 5, and `test/chaos/durability.test.ts` pins the property that justifies it: on a state with a lost commit Oracles 1-4 all pass and Oracle 5 does not. ADR-0022 names four Oracles; this adds one and leaves the four as they were.

**It reads one HTTP answer, in one direction.** ADR-0022's rule is that the verdict is never inferred from responses, because a Fault makes them lie both ways. A `201` can describe state a later kill never let persist; that is exactly what this Oracle exists to catch, so it takes the `201` (the Booking id in its body) as a *promise* and asks the stored state whether it was kept. A response can only ever convict here: a state with no `201` behind it proves nothing to this Oracle, and a `201` that the database agrees with is not itself evidence of anything beyond "kept". What stays out is the use ADR-0022 forbids, a response taken as proof that the system is fine. For Holds the promise is weaker (an acknowledged Hold may legitimately be gone because it expired, or because it was confirmed), so the Oracle accepts a Hold that is live, became a Booking, or was past its `held_until`, and requires an acknowledged Confirm's Booking to exist.

**It must run before the replay.** The replay re-sends every key, and a lost Booking is re-created under a new id, which would hide the loss. Oracle 5 therefore runs first, on the state as the restart left it, and matches by the *acknowledged id*, not only by key, so "re-created" cannot pass for "survived".

**The run owns its database, and its load is not k6.** Restarting a server takes every database on it down, so unlike C1-C3 this cannot share the dev Postgres or sibling sessions' containers. Each run creates `c4-pg-<hex>` on a free loopback port and the Fault driver re-checks the container's id, generated name and a run label against what it created before every stop, kill, start and remove; it never accepts a name from the caller. The load is a sustained Node client (`restartLoad.ts`) because the k6 scripts fire each request once and finish in a few hundred milliseconds, and because the per-request record of which Booking id was promised is what Oracle 5 needs and k6's point output cannot supply. The client follows the retry contract of ADR-0025/0026 (same key on a `502`/`504`/no answer).

**The negative control weakens the server, not the code (ADR-0023).** A hard kill of stock Postgres is not supposed to lose a commit, so a control that "should" fail needs a database that can: `synchronous_commit=off` with `wal_writer_delay=10s` and `wal_writer_flush_after=1GB`, so an acknowledged commit exists only in server memory for up to ten seconds, plus `fsync=off` and a one-hour checkpoint interval. The same weakened server restarted *orderly* is the reference that must stay green, which shows the control's red comes from the kill. Nothing in `src/` or `db/schema.sql` changes.

## What this cannot show

`docker kill` ends the Postgres processes; the Linux VM's kernel and page cache survive, so every WAL write the server had already handed to the OS is still there. The test is "the server process dies", not "the machine loses power", and `fsync` is not on its path (which is why `fsync=off` is not what loses commits in the control). Testing a lying disk or a power cut would need a way to drop the volume's page cache that this harness does not have. Exhibit H's section N and `formal/README.md` say so next to the result.
