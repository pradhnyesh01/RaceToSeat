# Formal verification is small-scope TLA+ over an abstract claim primitive, joined to the code by a hand-audited mapping with a drift test

Phase 6's formal track has to say something checkable about a seat-booking protocol whose real implementation is TypeScript issuing SQL against Postgres, without becoming a second project. Four decisions define what the models claim and how far that claim reaches; the results are in [Exhibit G](../evidence/exhibit-g-phase6-formal.md).

**Small-scope model checking, not unbounded proof.** The models are TLA+ checked exhaustively by TLC within fixed bounds: 3 requests, 3 seats, seat sets of 1–2 (and, for the crash layer, 2 keys and up to 3 Faults; its liveness runs are reduced further to 2 seats, 1 key, 1 Fault). `Init` ranges over every assignment of seat sets and request profiles instead of fixing a scenario, so every contention pattern in the bounds is covered, not the ones someone thought of. The bet is the small-scope hypothesis: protocols of this kind fail at two or three participants, and the negative controls corroborate it (every counterexample is 3 to 12 states). The cost is that nothing is claimed for larger N, wider seat sets, or the 1,000-client loads of Exhibits A–F; those stay load-test evidence.

**An abstract claim primitive, in separate modules.** `SeatBooking.tla` models the claim of a seat as an abstract atomic step (`ClaimMode = atomic`), which stands for `SELECT … FOR UPDATE NOWAIT` and `pg_try_advisory_xact_lock`, and proves mutual exclusion and atomicity once; the other three modules (blocking acquisition and deadlock, the Hold → Confirm → Reaper lifecycle, crash and idempotent retry) take that all-or-nothing claim as one step. This keeps each state space tractable and means optimistic locking's version column, advisory lock keys, and serializable's SSI are deliberately not modelled: the project's deliverable is a comparison of six mechanisms, but the formal claim is about the *contract* they share and about the `pessimistic` hold flow (ADR-0017), not about reproducing Postgres. Separate modules also mean F1's results are never re-opened by a later model. The price is a layering assumption (F1's result transfers into F3/F4) that Exhibit G states instead of hiding.

**A negative control for every checker, and none of them in production code.** An invariant never seen to fail proves nothing, so every positive check has a variant that must go red for the named reason: a mutated `.cfg` constant (no expiry check, a stale reaper, no key lookup, a lost commit, unsorted blocking acquisition), a vacuity guard showing the interesting state is reachable, and, for liveness, a variant that drops one fairness assumption. `check.sh` accepts a control only if TLC exits with the expected code *and* names exactly the expected invariant, so a parse error or the wrong violation cannot pass for "violation found". This is ADR-0023's rule applied to the formal track: the controls mutate the *model*, never `src/`. Where a violation is intentional because the behavior it names is real in the implementation (the idempotency key's lifetime, a spurious 409 on a concurrent retry), it is recorded as a named finding in the same machinery, not as an exception to it.

**A hand-maintained spec-to-code mapping with a drift test, not trace validation.** The model is joined to the implementation by a table in Exhibit G: each spec action, the SQL statement and `file:line` that implements it, a short literal anchor snippet, and a statement of where the spec is coarser than the code. It is audited by reading both, pinned to a commit, and guarded by `test/formalMapping.test.ts`, which parses the table out of the exhibit itself and fails if a cited anchor disappears (the code was rewritten: re-audit), drifts from its cited line (update the number), or if a spec action has no row. What this does not do is prove the code matches the spec. The honest reading is a reviewed claim plus a tripwire.

**TLC in Docker with a pinned jar.** `formal/check.sh` downloads `tla2tools.jar` v1.7.4 on first use, verifies its SHA-256 against `formal/tla2tools.pin`, and runs it inside a JRE image pinned by manifest digest, so a result is reproducible without a local Java and a later toolchain change cannot silently alter a verdict. The same script drives `npm run formal:check` (positive) and `formal:check:negative` (controls).

## Alternatives rejected

- **Unbounded proof (TLAPS, an inductive-invariant proof, or Apalache's symbolic checking).** Would remove the "small scope" caveat, at the price of finding and maintaining inductive invariants for four modules and their interaction — a project of its own, against todo.md's 25% share for all of Phase 6 and a cut order that already lists F4, the formal track's deepest layer, second. Kept as a possible follow-up, not a substitute.
- **Trace validation (replaying real executions, or DB logs, against the spec).** Would test the mapping rather than assert it, but needs instrumentation in production code or a faithful capture of Postgres's own interleaving, and each fix would have to be re-derived for six mechanisms. The mapping would also still be hand-written for the parts a trace cannot show. Rejected for cost, not for lack of value; the chaos track (ADR-0022) is the empirical complement that samples real executions.
- **Annotating the code with spec action names** (`// spec: AtomicClaim`) and generating the table. Puts spec vocabulary into production code for the benefit of a document, the same trade ADR-0023 rejected for test toggles, and an annotation can rot exactly as a line number does.
- **One monolithic spec**, or instantiating F1 inside F3 and F4. The combined state space of per-seat claim interleaving × lifecycle × crash × retry does not fit in the bounds; keeping the claim atomic above F1 is what lets the crash layer run at 3 requests and 3 seats.
- **Modelling blocking acquisition inside the booking spec.** Waiting changes the transition relation (a contended acquire is simply not enabled), so a blocking model and a fail-fast model answer different questions; `DeadlockFreedom.tla` is its own module so the fail-fast results in F1 are untouched.
- **A local Java and an unpinned TLC.** Cheaper to start, but makes "all checks pass" a function of whoever's machine ran it.

## Consequences

- Exhibit G must state, as part of its result, what the proof does not cover: the small scope, the hand-audited mapping, the abstracted mechanisms, the durability assumption (`CommittedPersists`, which chaos C4 was meant to test and was not run), the one-atomic-step Reaper, the single clock-free TTL, and the two real behaviors the model found (RF1, RF2).
- A change to `src/` that moves or rewrites a mapped statement fails `test/formalMapping.test.ts`, which is the intended prompt to re-audit the row against the spec; a change that keeps an anchor in place but alters semantics is invisible to it.
- A new spec action without a mapping row fails the same test, so extending the specs forces extending the audit.
- Where the model and the code disagree the model is not silently edited: an audit that finds the spec misrepresenting the code reports it (Exhibit G's observations O1–O3) rather than changing either.
